\begin{abstract}
This project runs a pretrained PointPillars detector on LiDAR scans and publishes
3D boxes through ROS 2. The software now supports Ubuntu 24.04, ROS Jazzy,
TensorRT 10 and an explicit Ouster channel adapter. Deployment, conversion and
visualization have been exercised on an RTX 4060 Laptop GPU. The latest labeled
comparison supports reflectivity divided by 255 as the experimental input;
neither tested channel is accepted as accurate 3D detection. This guide separates
how to run the system from what the measurements establish.
\end{abstract}
This edition consolidates the older deployment notes and dated appendices.
Historical experiment details remain in the Markdown reports and version history;
commands below describe the current launchers. It is a practical companion to
\path{docs/THESIS_DRAFT.tex} and the detailed Ouster decision report.

\section{Start here}
Use the Docker route if you want to run the application. Native development is
optional. A working host NVIDIA driver, Docker and NVIDIA Container Toolkit are
prerequisites; deployment does not install or upgrade them. RViz additionally
needs a graphical desktop, host ROS Jazzy and its detection display plugin.

\begin{tabularx}{\linewidth}{@{}lY@{}}
\toprule Item & Current role \\ \midrule
Host & Ubuntu 24.04, Linux x86-64; supplies GPU access. \\
Container & ROS Jazzy, CUDA libraries, TensorRT 10.16.1.11 and application. \\
ONNX & Pretrained network and weights; no retraining is performed. \\
Engine & GPU execution plan built from ONNX and cached persistently. \\
Ouster adapter & Selects a declared sensor field and creates FLOAT32 XYZI. \\
RViz & Displays points, predictions and count text; it does not run inference. \\
\bottomrule
\end{tabularx}

\section{Clone and prepare the image}
If the repository already exists, use that checkout and preserve local changes.
For a new checkout:
\begin{verbatim}
git clone https://github.com/AhmedAliMohammed1/MasterThesis.git
cd MasterThesis
nvidia-smi
sudo docker version
sudo env PP_BUILD_ONLY=1 bash tools/deploy.sh
\end{verbatim}
The last command prepares the image and exits. \code{PP_BUILD_ONLY=1} is optional:
without it, \code{deploy.sh} also starts the detector alone. For the Ouster route,
preparing the image first avoids starting a detector that must then be stopped
before the combined adapter/detector launcher.

\subsection{What is downloaded and what is reused}
The default deployment uses local source, including uncommitted runtime edits.
A matching runtime-input checksum skips Docker build entirely. Documentation-only
edits do not require a new image. Changed runtime files trigger a build that can
reuse independent dependency and model layers. A first build, removed cache or a
changed dependency recipe can require downloads. Driver installation is separate.
\begin{verbatim}
# Explicit options; normally unnecessary:
sudo env PP_FORCE_BUILD=1 PP_BUILD_ONLY=1 bash tools/deploy.sh
sudo env PP_PULL_BASE=1 PP_BUILD_ONLY=1 bash tools/deploy.sh
\end{verbatim}
A direct Dockerfile build retains its remote-source default. Use the deployment
wrapper for local development; a push is not required to test local runtime edits.
A fixed remote build can be selected with \code{PP_GIT_REF} and the full commit SHA.

\subsection{Engine lifecycle}
\begin{center}

\draw[arr] (model)--(check);\draw[arr] (check)--(engine);\draw[arr] (engine)--(runtime);

The ONNX is stored at \path{/opt/models/pointpillars.onnx}; engines are under
\path{/var/lib/pp_infer} in the named volume \code{pp-engines}. Cache identity
includes model, GPU, driver, software and build recipe. Partial builds use a
pending file and are not promoted on failure. An engine from another GPU or stack
should not be assumed portable. The host image and engine volume remain after
normal container shutdown.

\section{Replay the original Ouster recording}
The commands below use three terminals, all opened in the project root.
The downloaded originals must already be present; the player does not download
them. Their manifest and exact paths are recorded in
\path{docs/FRESH_OUSTER_VISUAL_TEST.md}.
\subsection{Terminal 1: adapter and detector}
\begin{verbatim}
sudo bash tools/start_ouster.sh bag
\end{verbatim}
This starts both processes in one container. The bag profile uses Fast DDS,
domain 99 and original input \code{/sensing/lidar/points}. It maps
reflectivity/255 into intensity on \code{/point_cloud}; the detector publishes
\code{/bbox}. The operating confidence threshold defaults to 0.4.
\subsection{Terminal 2: unchanged original bag}
\begin{verbatim}
sudo bash tools/start_ouster_bag.sh
# Alternative weather recordings:
# sudo bash tools/start_ouster_bag.sh rain30
# sudo bash tools/start_ouster_bag.sh rain100
\end{verbatim}
Default dry playback loops at half speed. The source bag is mounted read-only.
A warning about missing MCAP serialized metadata was observed during successful
playback; it did not prevent message delivery in the recorded test.
\subsection{Terminal 3: RViz on the desktop, without sudo}
\begin{verbatim}
ROS_DOMAIN_ID=99 RMW_IMPLEMENTATION=rmw_fastrtps_cpp \
  RVIZ_CONFIG="$PWD/rviz/ouster.rviz" \
  bash tools/visualize.sh -f lidar/os_lidar
\end{verbatim}
The fixed frame is the recording's \code{lidar/os_lidar}. A different sensor
requires its actual frame or a valid transform. The viewer starts only RViz;
it does not start playback or detection. To update an already open RViz window,
use File / Open Config instead of opening another process.
\subsection{Stop and restart}
Press Ctrl+C once in each launcher terminal and allow up to eight seconds for
cleanup. Close RViz separately. The launcher stops its own container and
preserves unrelated containers. If a name is already occupied, inspect
\code{sudo docker ps -a} before stopping the intended instance. Use one point-cloud
source per detector input and ROS domain.

\section{Use a working live Ouster driver}
The project consumes driver output; it does not power the sensor, configure its
network, start scanning or install a driver. Inspect the driver's topic, schema,
frame, domain, middleware and QoS before launching.
\begin{verbatim}
# Live defaults: /ouster1/points, domain 0, rmw_zenoh_cpp.
sudo bash tools/start_ouster.sh
# Example when the existing driver uses Fast DDS:
sudo env RMW_IMPLEMENTATION=rmw_fastrtps_cpp \
  OUSTER_POINT_CLOUD_TOPIC=/ouster/points \
  bash tools/start_ouster.sh reflectivity
\end{verbatim}
The live Zenoh profile requires a reachable router. Match the actual driver's
settings; do not mix the live and bag profiles accidentally.

The adapter always converts the selected channel. It does not automatically
choose the best channel or bypass itself when an intensity field exists.
\code{start_ouster.sh signal} selects a literal field named \code{signal} and
uses divisor 65,535. The downloaded MOSEP and Dur360 files instead name that
measurement \code{intensity}. A verified field alias is proposed, not implemented
in the live adapter. The research preparation handles the documented recording
schema explicitly; selecting signal in the bag launcher is not an equivalent
reproduction of that experiment.

\section{Understand the data path}
\begin{center}
\begin{tikzpicture}[node distance=6mm,font=\small,
 box/.style={draw=accent,align=center,text width=10.5cm,minimum height=9mm},
 arr/.style={->,>=Stealth,accent}]
\node[box] (raw) {Driver or player: original PointCloud2};
\node[box,below=of raw] (adapt) {Ouster adapter: validate fields; intensity = selected field / divisor};
\node[box,below=of adapt] (pack) {Detector CPU: validate and pack FLOAT32 XYZI};
\node[box,below=of pack] (gpu) {GPU: pillar features, PointPillars network and box decoder};
\node[box,below=of gpu] (out) {CPU: validate boxes, run NMS and apply publication threshold};
\node[box,below=of out] (ros) {ROS: accepted boxes, diagnostics and count text; RViz consumes them};
\draw[arr] (raw)--(adapt);\draw[arr] (adapt)--(pack);\draw[arr] (pack)--(gpu);
\draw[arr] (gpu)--(out);\draw[arr] (out)--(ros);
\end{tikzpicture}
\end{center}
The direct detector expects scalar little-endian FLOAT32 x, y, z and intensity.
The Ouster adapter additionally accepts supported uint8/uint16/FLOAT32 selected
channels, preserves XYZ and the source header, and creates a new compact XYZI
message. It does not edit the original bag. Keep detector intensity scale 1.0
when feeding already converted points; another division would change the recipe.

Malformed or oversized clouds are rejected. Valid row padding is supported;
nonfinite points are removed by the detector packer. Engine capacity is 204,800
points and the default cloud byte limit is 64 MiB. The detector callback remains
synchronous with reliable depth 700. The adapter uses sensor-compatible best-effort
input and reliable output. A bounded worker and general detector QoS configuration
remain open work; a large queue can accumulate delayed scans under load.

\section{Read boxes, counters and timestamps}
\code{/bbox} is a Detection3DArray of accepted boxes. \code{/bbox/stats} is a
DiagnosticArray; \code{/bbox/count} is an RViz MarkerArray with count text.
\begin{verbatim}
PP_MONITOR_BACKEND=docker bash tools/monitor_detections.sh once
PP_MONITOR_BACKEND=docker bash tools/monitor_detections.sh threshold
sudo docker exec pointpillars /entrypoint.sh \
  ros2 param set /pointpillars confidence_threshold 0.7
\end{verbatim}
The node/YAML default threshold is 0.5; launchers set 0.4 unless overridden.
Query the running parameter instead of assuming which default applies. Changing
this publication gate needs no engine rebuild. NMS runs first, so ``before filter''
means after NMS. Totals count repeated detection events, not unique tracked objects;
they reset on node restart. A dropped frame has unavailable output counts, while
a valid empty scan can publish zero. Retained diagnostic text may be old.

Detection timestamps and coordinate frames are copied from the input scan.
They describe the measurement reference, not the completion time. Camera and
LiDAR clock alignment is a separate problem. The pipeline does not implement
motion compensation, hardware clock synchronization or calibrated image overlays.

\section{Latest experiment and practical decision}
The 8 November study ran 1,120 measured GPU inferences plus 18 excluded warmups
through unchanged production C++ inference and NMS. It compared signal/65,535
with reflectivity/255 at a reporting threshold of 0.4. The study used 480 MOSEP
weather observations, 320 labeled Dur360 observations and 320 separate
capacity-control observations. Five repeated runs are not five independent scenes.
\begin{table}[htbp]\centering
\begin{tabular}{@{}lrr@{}}
\toprule Test vehicles, 16 scans & Signal/65,535 & Reflectivity/255 \\ \midrule
BEV matches per run, out of 60 & 0 & 4 \\
Mean BEV precision & 0\% & 27.81\% \\
BEV recall & 0\% & 6.67\% \\
Qualifying 3D matches & 0 & 0 \\
Recorded inference failures, all runs per channel & 0/560 & 0/560 \\
\bottomrule
\end{tabular}
\caption{A development preference, not an accurate 3D operating configuration.}
\end{table}
There are also zero qualifying pedestrian matches; no cyclists occur in the
selection. Labels are publisher annotations, described in the original paper as
model-assisted and human-reviewed. The published splits have disjoint frame
indices but are not established as independent drives. MOSEP is unlabeled.

Dur360 originally has 262,144 points per scan, beyond engine capacity. Identical
model-region filtering and zero-return removal reduced both channel variants to
65,238--175,559 points. This preparation differs from unchanged full-cloud
production playback and is documented explicitly. Twenty of 32 primary scans
still exceed 10,000 occupied pillars. A separate bounded-pillar control preserved
the four-versus-zero BEV result, with zero qualifying 3D matches for both channels.

\begin{figure}[htbp]\centering
\projectshot{ouster-channel-ground-truth-2026-11-08.png}{.98\linewidth}
\caption{Frozen middle test frame: actual predictions and independent publisher
annotations. Green denotes labels; orange/purple denote the compared predictions.
The XZ row exposes vertical displacement. Dur360BEV-Extended, CC-BY-4.0;

\end{figure}
The four first-repeat reflectivity vehicle BEV matches have centers
0.60--1.14 m too high. Their 3D overlaps are below the declared 0.7 criterion.
An arbitrary z shift is not justified. Use reflectivity/255 as the experimental
baseline while investigating valid returns, pillar capacity and model/input
conventions. Freeze a justified correction before testing on new, recording-disjoint
annotated data. If needed, select or fine-tune an Ouster-compatible model.

\section{Verification and recovery}
The comparison release records 119 passing Python tests. The earlier launcher
fix additionally records seven C++/ROS tests and actual GPU replay: 20 raw clouds,
20 adapted clouds and 19 detection arrays, with sampled error counters zero.
Each launcher stopped after one SIGINT in under half a second in that test.
These counts describe specific runs; they do not establish sustained reliability.
The new direct GPU comparison does not retest ROS transport. Its first ROS A/B
attempt was excluded after large-cloud UDP delivery loss.
\begin{verbatim}
python3 -m unittest discover -s tests -p 'test_*.py'
python3 tools/recovery.py status
git status --short
\end{verbatim}
For native work, use separate colcon build/install directories for CPU-only,
ROS-adapter and full-runtime configurations. Read \path{docs/local_runtime.md}
and the CMake options before building. Reduced adapter tests can run without a
GPU; inference requires the target-GPU engine. Do not reuse stale absolute-path
build caches after moving the checkout.

Large bags, models, engines and observations remain under ignored local storage.
A Git push does not back them up. Preserve originals, manifests and hashes
independently. Do not overwrite a completed experiment directory when changing
source, model, selection or evaluation policy.
