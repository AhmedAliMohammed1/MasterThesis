\begin{abstract}
This document explains the reasoning behind the project's current implementation
and experimental decision. It develops the earlier filtering and timestamp
discussion into a concise technical narrative that can support a thesis methods
and limitations chapter. It is an edited explanation, not a verbatim chat
transcript. The latest evidence favors reflectivity/255 over signal/65,535 for
vehicle bird's-eye-view detection in the tested configuration, while both fail
the declared 3D matching criterion. Software integration and scientific accuracy
are therefore reported separately.
\end{abstract}

\section{What happens when a scan arrives?}
A driver assembles the LiDAR returns into a ROS PointCloud2 message. For the
Ouster workflow, an adapter checks the selected fields and creates x, y, z and
intensity values for the detector. The detector validates that message, packs
its points and copies them to the GPU. PointPillars groups the points into
vertical pillars, extracts features and predicts candidate object boxes.
The CPU checks the candidates, removes overlapping predictions with NMS,
applies a confidence threshold and publishes the accepted boxes.

The conversion is explicit:
\begin{center}
\begin{tabular}{ll}
Reflectivity recipe & intensity = reflectivity / 255 \\
Signal recipe & intensity = signal / 65,535
\end{tabular}
\end{center}
Each value comes from the selected field in that point's recorded schema.
These are fixed experimental encodings, not proof of physical reflectance
calibration or the model's ideal training distribution. A generic field called
intensity must not be assumed to contain the required signal measurement without
checking the sensor metadata.

The current adapter selects a literal signal or reflectivity field. MOSEP and
Dur360 name signal intensity; the research preparation handles that known schema.
A production signal-field alias is proposed but not implemented. The launcher
does not automatically detect the best feature, fuse channels or bypass the
adapter when XYZI is already present. A verified compatible XYZI source can
instead feed the detector directly.

\section{Why are there two filtering steps?}
\subsection{Non-Maximum Suppression removes overlapping proposals}
Several candidate boxes can describe the same surface or object. NMS ranks
candidates by score, considers at most 4096 and repeatedly keeps the highest
remaining score while suppressing boxes that overlap it. The current call is
class-agnostic and uses rotated ground-footprint IoU with threshold 0.01.
\begin{quote}
BEV IoU = area of the intersection / area of the union.
\end{quote}
The union area is the sum of the two footprint areas minus their intersection.
Height is absent from this overlap calculation. Increasing the NMS threshold
usually permits more overlapping proposals. It does not move boxes or repair
vertical position. On 192 earlier identical-candidate observations, the project
and pinned NVIDIA NMS selected identical boxes. Broad localization errors should
therefore be investigated before tuning suppression.

\subsection{The publication threshold controls what consumers receive}
After NMS, the node keeps boxes with a score at or above the selected threshold. The node/YAML default is 0.5;
current deployment launchers use 0.4 unless overridden. Query the live parameter
when recording an experiment. This extra gate can be changed without rebuilding
the engine. Disabling it with 0.0 does not disable the decoder's own model-level
candidate threshold.

\begin{center}
\begin{tikzpicture}[node distance=7mm,font=\small,
 box/.style={draw=accent,align=center,text width=10cm,minimum height=10mm},
 arr/.style={->,>=Stealth,accent}]
\node[box] (nms) {Valid post-NMS proposals: N};
\node[box,below=of nms] (gate) {Publication gate: retain scores at or above threshold};
\node[box,below=of gate] (pub) {Publish K boxes; report N minus K removed};
\draw[arr] (nms)--(gate);\draw[arr] (gate)--(pub);
\end{tikzpicture}
\end{center}
The before-filter count means after NMS. Cumulative published totals sum accepted
detection events over scans; the same car can contribute repeatedly. No tracker
turns these totals into unique objects. A valid empty frame can report zero;
a failed frame has unavailable output counts. Counts and confidence are useful
for debugging but cannot establish ground-truth accuracy.

\section{How do timestamps and coordinate frames work?}
The timestamp is a measurement reference supplied by the driver. It does not
command the sensor to begin scanning. A scan contains returns acquired over a
finite interval; a driver's cloud timestamp may refer to the start, end or
another documented reference. Individual point times, when available, describe
additional timing detail.

The detector copies the source timestamp and frame to its output. For example,
a scan referenced at 10:00:00.100 might finish processing at 10:00:00.150 while
its detection header remains 10:00:00.100. That associates boxes with the source
measurement. It does not measure inference latency by itself.

\begin{tabularx}{\linewidth}{@{}lY@{}}
\toprule Concept & Meaning \\ \midrule
Acquisition reference & When the driver says the scan belongs on its sensor clock. \\
Bag record time & When a recorder stored the message; playback can schedule by this time. \\
Processing completion & When inference finished; distinct from source header time. \\
Coordinate frame & Axes in which points and boxes are expressed. \\
TF transform & Relationship between coordinate frames, possibly time-dependent. \\
\bottomrule
\end{tabularx}
Preserved headers do not prove that LiDAR and camera clocks agree. The older
Ouster camera experiment found different header clocks. Coordinated playback
uses recorded arrival timing but does not establish acquisition synchronization.
The project does not currently implement hardware synchronization, point-wise
motion compensation or calibrated camera-box overlays.

The live sensor must be powered, connected, configured and served by a compatible
driver. This project subscribes to its messages; it does not issue hardware
scan-start commands. The correct driver command depends on the actual sensor
installation.

\section{Why can RViz draw boxes now?}
The node publishes standard Detection3DArray messages. The official
\code{vision_msgs_rviz_plugins/Detection3DArray} display reads those messages
and draws boxes directly. The launcher makes the plugin available and loads a
saved profile. MarkerArray is used separately for count text, not as a required
conversion of every detection.

RViz needs matching middleware/domain, compatible QoS and a valid fixed frame.
For the original MOSEP bag, use domain 99, Fast DDS and
\code{lidar/os_lidar}; the KITTI profile instead uses velodyne. The viewer
launcher defaults Fast DDS transport to UDPv4 because shared-memory delivery
failed in the earlier host/container setup. Large-cloud UDP delivery later
limited the attempted live ROS A/B test; changing transport does not guarantee
all deployment arrangements will work.

\section{What does stable mean in this project?}
Three distinct questions require different evidence:
\begin{enumerate}
\item \textbf{Numerical validity:} Does inference finish with finite, valid boxes?
\item \textbf{Repeatability:} Do repeated executions of the same input agree?
\item \textbf{Accuracy:} Do predictions match independently supplied object labels?
\end{enumerate}
A detector that consistently returns no boxes can be numerically successful and
repeatable while missing every object. Empty outputs must be reported separately,
not counted as ideal object agreement. Likewise, high confidence is a learned
score, not a calibrated probability that a box is correct.

The October study found raw signal failures in 15 of 48 observations; normalized
variants had no recorded failures. That motivated normalization but could not
rank accuracy because those recordings lacked object labels. The 8 November
study adds independent annotations and separates these questions explicitly.

\section{How was the latest comparison controlled?}
\subsection{Inputs and repetitions}
The comparison uses 48 MOSEP scans across dry, 30 and 100 mm/h rain conditions,
and 32 Dur360BEV-Extended scans: 16 from each published split. Two channel
variants and five repeats give 480 MOSEP and 320 primary labeled inferences.
Another 320 labeled observations test a separate bounded-pillar policy. In total,
1,120 measured GPU inferences were recorded; 18 warmups were discarded.

Both variants retain identical XYZ bits, point order and count within an
experiment. Only the fourth feature changes. Order is shuffled with seed
20261108. The unchanged production C++ inference/NMS runs with the existing FP32
engine, NMS 0.01 and top-N 4096; all post-NMS rows are saved before the additional
publication gate. The direct runner isolates inference from ROS delivery loss.
It does not replace separate adapter or live integration tests.

MOSEP primary inputs retain original zero returns. Dur360's original 262,144
points exceed the engine's 204,800 limit. Identical model-region filtering and
all-zero-XYZ removal reduce both variants to 65,238--175,559 points. This is
explicit research preparation, not unchanged full-cloud deployment.

\subsection{Ground truth and evaluation}
The Dur360 paper describes model-assisted labels reviewed and supplemented by
experienced annotators. The Extended release supplies compatible labels but does
not separately detail its annotation procedure. These labels are independent of
our predictions; they should not be described as purely manual metrology.
Published train/test indices are disjoint within one collection, with no verified
independent-drive separation.

Matching is class-aware, confidence-ranked and one-to-one, using rotated BEV or
3D IoU. Vehicle needs IoU at least 0.7; Pedestrian needs at least 0.5. The declared
region has x/y in [−50,50) m and z in [−1.4,4.4) m, applied to centers of both
annotations and predictions. Of 70 original test cars and seven pedestrians,
60 vehicles and six pedestrians are included. Two cars fall outside XY; eight
more cars and one pedestrian fall outside z. There are no cyclist annotations
in the selected scans. Exclusions are reported rather than silently counted as
successful detections.
\begin{quote}
Precision = TP / (TP + FP).\\
Recall = TP / (TP + FN).
\end{quote}
Here TP counts matched predictions, FP counts unmatched predictions and FN counts
missed annotations.
Repeated runs use the same scenes. Report mean run ratios and repeat ranges;
do not multiply the effective scene sample size by five. Diagnostic continuous
AP differs from KITTI AP\_R40 and is not an official Dur360 score.

\section{What does the capacity control tell us?}
Twenty of 32 primary labeled scans exceed 10,000 occupied pillars; every scan
also contains pillars with more than 32 points. A separate geometry-only control
keeps the first 10,000 encountered pillars and first 32 points per pillar in
original order, identically for both channels. This mechanical selection does not
reproduce CUDA thread encounter order.

The control removes empty/nonempty changes between repeats in this sample.
It still yields four versus zero vehicle BEV matches and zero qualifying 3D
matches at 0.4. Reflectivity mean BEV precision falls to 21.99\%. Capacity handling
therefore affects repeatability but does not solve accuracy or improve every
metric. This control has not been installed in production preprocessing.

\section{A defensible next step and thesis interpretation}
Keep reflectivity/255 as the experimental baseline for this configuration.
The proven scope is a measured vehicle BEV advantage over this fixed signal
encoding on a small diagnostic subset. Neither universal channel superiority nor
acceptable 3D detection has been demonstrated.

Next, declare a valid-return and capacity policy; investigate sensor origin,
training coordinates, anchor/decoder conventions and reference-model behavior.
Any change must have an independent rationale rather than being fitted to the
inspected test labels. If the fixed model remains unsuitable, select an
Ouster-compatible model or fine-tune using a separate training set.

Freeze the resulting recipe and evaluate a new recording-disjoint annotated
sample. Include negative scenes, varied distances/weather and enough supported
class examples. Report localization errors, per-class BEV/3D precision, recall,
AP, failures and latency. A pilot target of at least 80\% precision and recall
at the declared 3D IoU is proposed for discussion; it is not an agreed requirement
or a universal safety standard.

For thesis writing, separate three contributions: the software migration,
the explicit sensor adapter and the controlled channel investigation. A negative
3D result is a valid research finding when the method, exclusions and limitations
are disclosed. Do not present an RViz screenshot, box count or successful test
suite as an accuracy result.
